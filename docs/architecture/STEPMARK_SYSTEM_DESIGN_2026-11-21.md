# StepMark 整体系统设计与可执行实施方案

> 更新：2026-11-21。基于主分支现存代码核查。本文区分「已经有代码的功能」「研究型原型」「上线前待完成」。这是工程说明，不构成心理测量效度、医疗效果或商业运营就绪证明。

## 1. 产品定位与边界

StepMark 由「能力测评」「长期习惯证据」「AI 对话式记录」「复盘反馈」组成。它要帮助用户发现问题、持续练习并用可复查证据观察变化，而不是从聊天、重复打卡或 AI 的主观语言里凭空生成一个精确的「综合智商」分数。

设计原则：
1. 用户拥有自己的数据，任何读写均根据服务端认证的 User.id 授权。
2. 把行为发生、习惯自动性、题目表现和潜在能力分成四种不同的证据，不让前一种自动推高后一种。
3. 计分公式、题目和评价策略都标注版本；不同版本不能未经校准直接混合。
4. AI 只分析当前允许的文本和本人的习惯列表；它建议结构化操作，服务端验证后才进行有限写入。
5. 交互尽量聊天优先，但关键个人数据变更应可查询、导出、更正和删除。
6. 先做模块化单体，而不是在小规模阶段拆出多个微服务。

## 2. 当前真实架构

~~~text
手机微信小程序 ────────┐
浏览器/响应式网站 ─────┼── HTTPS ── Caddy ── Next.js Node API
Windows 桌面客户端 ────┘                      │
                                           ├─ Auth/Authorization
                                           ├─ Habit & Event Service
                                           ├─ Assessment & Practice Service
                                           ├─ Assistant Command Gateway
                                           └─ Reporting / Export / Deletion
                                                     │
                                            Prisma ORM + Pg Adapter
                                                     │
                                                 PostgreSQL
                                         （账号、会话、行为、题目、证据）
                                          只在用户明确同意时
                                                     │
                                         OpenAI/OpenRouter/兼容服务商
~~~

实际工程结构：
- packages/core：无数据库依赖的确定性统计、心理测量模型、习惯曲线、评估和研究模块。
- packages/contracts：共享 Zod 数据契约、输入约束、可版本化字段。
- apps/web：Next.js 16 + React 19 + Node.js API，包含账户、习惯、题目、AI、仪表板。
- apps/wechat-miniapp：wx.login + 后端换取微信身份，以及同一版本 API；微信小程序不持有服务端密钥。
- apps/desktop：Tauri/Rust 原生请求层 + Windows 凭据管理器；目前只读，不允许客户端直接写数据库。
- apps/web/prisma：PostgreSQL schema 与顺序迁移。
- deploy：单 ECS、Caddy、公网入口、私有 Node 监听、外部受管数据库的部署模板。

这是「一个共享后端，多个终端」，而不是每个客户端各建一份账号、公式和数据库。

## 3. 核心数据模型

- User：服务端主身份；Credential（邮箱、scrypt 哈希与验证）、ExternalIdentity（微信 OpenID 等）、Session（令牌哈希和到期时间）。
- Habit：用户、名称、动作、触发情境、复习开关、归档时间；HabitEvent：可用机会/完成与时间，唯一键为 (habitId, opportunityKey)；HabitEventCorrection：事件修订记录（revision 比较并交换）。
- HabitReflection：用户原话、可选的用户主动评分、是否同意第三方 AI、AI 处理状态和初步注释；AutomaticityCheck：独立四题自评量表的答案与索引。
- Construct、Task、AssessmentAttempt：能力维度、不可随意修改的题目版本、一次性答题；AIJudgement：暂定 AI 评价与人工复核状态；AbilityEstimate：保留模型版本和估计不确定性，不能由打卡直接写入。
- PracticeAttempt：练习题正确性、是否使用提示、日期和题库版本；与正式测评表分离。
- AssistantAction：结构化 AI 写入回执，唯一键 (userId, requestId)，保存消息摘要与变更结果但不保存完整聊天正文。
- RateLimitBucket、LoginCode、VerificationToken：限流、微信验证码防重放、邮箱验证/重置令牌。

数据可导出：账户 export API 按类别、按用户、每页 100 条返回。删除账户会删除个人所属主数据以及相关审计明细。以上是代码级逻辑；提供商已接收的数据、备份中的数据还需结合真实服务合同和留存政策处理。

## 4. 习惯量化：何时算执行，何时算自然

第一层：行为机会。每个有效机会记 eligible=1，实际做了记 completed=1：
- n = Σ eligible；s = Σ (eligible × completed)
- 完成率 r=s/n；没有机会时 r=null，不能当作未执行或 0%。
- 给出 Wilson 95% 区间作为「观察完成比例」的描述性不确定性；连续几天并非完全独立样本，不能误称个人能力置信区间。
- 使用 Beta(1,1) 先验的示意后验 Beta(1+s,1+n-s)，均值 (s+1)/(n+2)，并明确标记 descriptive。不能解释为「习惯已经形成的概率」。

第二层：主动启动的感受。用户可选择 0~4 等级，分别按演示策略映射为 0、15、35、70、100。服务端仅选最近 12 个不同 UTC 日期的用户主动评分；同一天重复回答不叠加证据强度。使用相对最新评分的半衰期 35 天权重，对这 12 份证据加权；AI 从日记推断的等级绝不自动充当用户亲自评分。

第三层：页面成长指标，现有 policy=habit-progress-v2：
- 重复信号 R(n)=100×(1-exp(-n/55))。
- 自评自然启动信号 A 为上述加权均值，无自评时 A=null。
- 原始显示值 G=0.45R+0.55(A 或 0)。
- 上限：没有自评 45；一天自评 65；两天自评 80；三天以上且时间跨度不足 14 天为 85；跨度足够为 96。
- G 再截断到 [0,上限]，保留一位小数。上述系数和上限是产品启发式策略，不是 Lally 论文给出的已校准阈值，不得标注「养成率」或「能力百分位」。
- 45 天没有新主动评分标记证据陈旧；低证据常规约 7 天提醒、一般约 14 天、较稳定约 28 天、近期困难约 6 天，且只能提醒不能强制用户填报。
- 4 项 1~7 分的自评索引独立计算：100×(mean(q1…q4)-1)/6；它仅为实验性展示索引，不能直接叫「验证过的 SRBAI 分数」。

第四层：曲线研究。使用 H(n)=H0+(Hmax-H0)(1-exp(-kn)) 拟合重复次数与实际自评自动性；限约束 0≤H0≤Hmax≤100、0<k≤1。代码采用网格搜索及近似 AICc 比较常数模型，用来观察个体变化趋势；不能据此承诺「第 66/90 次就形成习惯」。

## 5. 能力量化：题目表现 ≠ 潜在能力

能力维度不是直接混成一个总分。已有研究/代码包含 reasoning.logic、expression.structure、attention.control 等注册表和实验性模型：
- 题库：服务端保存题目版本、发布状态、完整答案及校验信息；只将题面/选项返回给客户端。独立 A/B 逻辑表需按进度释放反馈，避免答案泄露影响后续测试。
- 测评：目标是可重复的独立任务、相同测量条件、题目校准和研究级版本冻结。当前少量演示题仅能显示任务级表现。
- IRT 2PL 题目正确概率：P_i(θ)=1/(1+exp[-a_i(θ-b_i)])，其中 a_i 为区分度，b_i 为难度。信息量 I_i(θ)=a_i²P_i(1-P_i)。
- 研究型 EAP 采用 N(0,1) 先验，在 [-4,4] 的 161 点网格数值近似计算 θ、方差和模型后验区间。必须具备独立校准、测量等值性与适当人群验证，才能考虑面向用户展示 θ/百分位；当前正常用户能力发布由代码阻断。
- 表达评分：固定行为锚定的 0~4 Rubric、正权重 w，任务分数 100×Σ(wr)/(4Σw)。AI 作答判卷只可作为待复核证据，需与人工评分比较一致性后决定进入能力模型。
- 预测能力：记录预测概率 p 与事后实际结果 y∈{0,1}，用 Brier 均方损失平均 (p-y)²；基准预测必须在事件揭晓前冻结，比较同类事件才有意义。
- 训练与能力：完成打卡、某套题练熟不能证明跨任务迁移。应安排陌生题、延迟复测、对照条件及模型误差校准，再评估能力是否真正改善。

## 6. 聊天驱动数据变更的完整安全链

1. 浏览器/微信客户端传入当前消息、随机 requestId、当地日期和明确的 AI 传输同意。
2. 服务端验证会话/令牌、正文大小、字段结构、频率及归属用户。它只提取本人的习惯名称与 ID。
3. 服务器通过固定、已配置的第三方 API 出口发送当前必要信息；设 12 秒级超时和响应字节上限，拒绝重定向及不受信 URL。
4. 模型只能返回六类结构化意图：create_habit、record_opportunity、record_reflection、check_progress、chat、clarify。其他行为必须拒绝。
5. 服务器不信任模型决策：检查语义是否得到用户当前消息明确授权、目标习惯是否归属本人、日期和状态是否允许；无法判断时不写入、要求澄清。
6. 涉及写入时由数据库事务提交，(userId,requestId) 保证网络重试不重复扣减/重复登记；可由 correction API 修订事件并保留历史。
7. 普通聊天不存正文；只有有限操作回执被保存以支持可审计的去重。后台日记 AI 注释由独立任务工作器处理，不拖慢 GET 页面。
8. AI 推断的心理状态不能自动生成正式的自评分、能力 Estimate 或医疗结论。

剩余设计缺口：对话式操作需要真人话语基准集验证意图分类错误率、误写率、拒写率；多并发不同 requestId 对同一业务操作的上限需要监控。生产部署还需清晰说明第三方 AI 服务商及数据流向。

## 7. 三种客户端与权限

- Web：浏览器 HttpOnly、Secure（生产）SameSite=Lax Cookie；修改操作要求同源 Origin，CSRF 防护；网页可看成长面板、题目与习惯记录。
- 微信小程序：wx.login 产生一次性 code，服务器交换 OpenID，避免将 AppSecret 放在小程序；会话使用 Bearer；业务请求继续由统一 API 做 owner scope。
- Windows：Tauri/Rust 原生联网并通过系统默认浏览器走带 PKCE 的回调授权；短期授权码只使用一次，真正令牌由原生 Windows 凭据管理器保存，前端 WebView 拿不到令牌；首期仅 GET /me 与 GET /habits，无写操作。
- 各端共享同一 User.id 对应的数据。微信账号与邮箱账号的主动合并流程仍需单独设计和安全验证，不能凭邮箱文字相同就自动合并。

## 8. 安全与审计设计

身份：邮箱地址规范化、scrypt 密码哈希、不可逆哈希会话令牌、密码重置后撤销旧会话、微信 code 防重放、桌面 PKCE。
授权：所有用户资源查询必须带服务端 userId。桌面只读权限不得因 cookie、请求头或路径组合而扩大。
输入：Zod 严格验证、流式限制请求字节、拒绝超大正文；不把数据库异常、令牌、AI 提示词或原始聊天文本写入公开错误。
反滥用：按时间窗、IP/用户/邮箱等维度对敏感操作进行原子数据库限流；触发 429 后返回 Retry-After，便于客户端退避。
边界：Caddy 是唯一公网入口，Node 3000/数据库不能暴露。当前部署文件仅支持 DNS-only 的直连 Caddy 模式；接入 Cloudflare 橙云之前必须验证 Cloudflare IP 源、可信客户端 IP 转发、禁止直接访问回源，并重做限流审计。不能只信任客户端送来的 CF-Connecting-IP。
保密：第三方 AI 密钥、邮件密钥、微信密钥仅在服务端环境；HTTP API 私有响应 no-store；控制日志和研究数据授权。
供应链：CI 的 npm audit 需要持续通过。近期 Effect 依赖补丁固定 3.22.1 并附加 package-lock 回归测试，避免漏洞重现（仍需以最新 CI 为准）。

## 9. 性能设计与容量策略

1. 热路径：已登录 GET 接口只做必要的数据库查询、固定 take 上限、索引与批量聚合；不在页面 GET 调用 LLM。
2. 数据库：Prisma + pg 驱动；一个 Node 进程只有一个复用客户端，默认连接池最大 6（可配置 1~12），降低小实例的连接争用。生产使用 ECS 与 PostgreSQL 同地域，优先私网连接和真实 TLS 验证。
3. 查询：Habit 列表取最多 50 个活跃项；复习队列先查当前账户习惯，然后按 habitId 聚合统计，不对每个习惯发 N+1 请求；保留合理的事件/反思/任务索引。
4. 缓存：公开版本化 catalog 可以静态缓存；私人账户、习惯、评分、行为、导出和 AI 响应不得被跨用户缓存。
5. 观测：分别采集 p50/p95/p99、数据库池排队、错误率、AI 超时率、队列积压、每用户每小时写入量、429 分布、回源异常；日志脱敏。
6. 压测：现有 perf-http 仅在 localhost 对少量只读路径做冒烟测试，不能当作国内/海外用户真实延迟指标。真实上线前从中国大陆及目标海外国家分别做测量。
7. 初期架构仅用于小规模流量；不能从 CI 成功推导几十万人并发的吞吐量。边缘 WAF/限流、攻击防护和容量规划必须另行验收。

## 10. 生产部署与运行步骤

阶段 A（准备）：确定面向地区和数据驻留规则；购买合法可用的服务器与托管 PostgreSQL；核对域名解析、HTTPS 证书、个人信息告知、第三方 AI 跨境传输以及中国大陆适用的备案要求。
阶段 B（连接）：在云安全组只开放 Caddy 必要入口，数据库只接受应用私网地址；配置最小权限 DB 用户，运行迁移账户与运行账户分离；生成 32 字节随机 RATE_LIMIT_SECRET。
阶段 C（初始化）：通过 npm ci --ignore-scripts、npm run db:generate、npm run db:deploy --workspace @stepmark/web、npm run db:seed --workspace @stepmark/web 完成依赖、客户端、迁移与初始演示数据。先在测试库演练，检查 schema 与滚动部署兼容性。
阶段 D（验证）：填写 deploy/production.env，运行 apps/web/scripts/production-preflight.mjs；用 deploy/compose.yml 与 Caddyfile 启动 Web 和反向代理。检查 /api/health（仅进程存活）和数据库连通性（需独立私有验收），再做登录、数据隔离、导出/删除、密码重置、微信登录和 AI 同意流程。
阶段 E（后台任务）：可靠地每日运行 db:prune；需要 AI 日记处理时单独调度 habits:analyze，并设工作器失败告警。检查数据保留期限、失败重试与撤回同意。
阶段 F（上线运行）：DB 自动备份 + 定期恢复演练、资源阈值告警、镜像回滚计划、错误率/SLO、滥用处理、证书轮换和权限审计。若引入 Cloudflare 橙云，需另开可信代理工程并通过对应回归测试。

## 11. 验收与测试矩阵

已自动化的范围包括：packages/core 确定性公式和研究脚本、Node/API 多用户权限与操作重试、邮箱/微信/桌面授权、原始题目版本和私有研究资料隔离、服务端请求与输出边界、微信 JS、Windows Rust、Docker 镜像与 Compose 模板、依赖安全审计。

上线前仍需专门做：
- 人工黑盒安全测试：越权/多租户/CSRF/会话劫持/令牌泄露/开放重定向/第三方模型提示注入。
- 中国大陆与海外真实网络测速：登录到首屏、操作到确认、模型调用及远程 DB；不要混用本地冒烟结果。
- 邮件可达性、微信真实机体验、Windows 安装包签名、隐私政策与跨境合规。
- 备份恢复：校验随机数据恢复、RPO/RTO、事件修订历史和账号删除一致性。
- 心理测量：独立验证样本、可靠性、效度、性别/地区/时间测量等值性、正式数据集许可及样本外预测，不把训练收益混同为广义能力变化。

## 12. 下一步实施优先级（不夸大完成度）

P0（发布前必须）：CI 与漏洞审计持续绿灯；正式环境 WAF/可信 IP 链；备份恢复演练；监控告警；邮箱/微信真实服务验证；隐私及合规文本；主库最小权限。
P1（产品质量）：聊天操作评估集、容错重试和多用户并发压测；跨端身份关联授权；更多独立练习项目；自主输入减少时保持证据可解释。
P2（研究深度）：纵向重复测量、习惯启动与执行分离、对照/交叉实验、IRT 题目校准、基准模型、AI 评价与人工判分偏差审计、不同语言人群的公平性检测。
P3（规模化）：在实测瓶颈出现后引入队列/缓存/CDN 等组件，而不是提前拆微服务。

## 13. 本轮已实现的工程性改进

- 将 Prisma 传递依赖 Effect 固定在安全补丁 3.22.1，并对 lockfile 增加回归检查，防止已披露 ReDoS 漏洞版本回退。
- 服务端在操作被限流时返回 Retry-After 秒数；不会暴露 rate-limit bucket 标识。
- 标准网页入口、列表查询和 AI 新建习惯统一使用 MAX_ACTIVE_HABITS=50；相应的集成测试覆盖 50 条列表与第 51 条拒绝。
- 坚持所有改动直接提交到 main。本文不会把 GitHub CI 的进行中状态写成「已通过」。

## 14. 核心结论

当前 StepMark 已是有真实账号、服务端权限、存储、行为证据、题目引擎与跨端入口的工程原型。它尚未在真实人群中获得「全面量化人的能力」所需的心理测量学验证，也不能在云资源和合规配置未就绪时宣称正式上线。正确路线是「稳定的账户与数据安全 → 可重复的证据收集 → 科学校准 → 可解释的个人变化 → 上线容量与合规验收」。
